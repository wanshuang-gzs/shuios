## V1 · Rust 组件跨目标类型检查

**命令**

```powershell
rustup target add x86_64-unknown-linux-gnu
cargo check --workspace --target x86_64-unknown-linux-gnu
```

**原理**：Windows 上装 Linux 的预编译 std 后，`cargo check` 只做类型检查、
不链接，因此不需要 Linux 链接器，却能提前抓出所有编译错误。

**结果**：一开始 1 个硬错误 + 3 个警告，全部修复后通过。

| 文件 | 问题 | 修复 |
| --- | --- | --- |
| `crates/shui-ctl/src/main.rs:148` | `let v = call(...)` 泛型返回类型无法推断 | 6 处显式标注 `serde_json::Value` |
| `crates/shuiosd/src/config.rs` | `Config::pretty` 未使用 | 删除 |

**命令**

```powershell

cargo test -p shui --lib       # 14 passed
```

**覆盖的行为**

* 请求信封：`id` 为 `None` 时不得出现在 JSON 里
* 响应信封：`result` 与 `error` 互斥，错误码 `-32001`
* 枚举序列化：`AgentState` → `"running"`、`Capability` → `"fs_read"`

* `ToolResult` 结构稳定（成功不带 `is_error`）
* `parse_endpoint`：带端口 / 不带端口 / 拒绝 `https://`
* HTTP 响应解析：头部切分、chunked 解码、纯 Content-Length
* 工具调用解析：`tool`/`name` 别名、`arguments`/`args` 别名、缺参数、
  夹在自然语言里、**普通 JSON 不当成命令**（要求工具名带点号）、

## V6 · 镜像组装方案对齐 Buildroot 官方实现

对照 `board/pc/genimage-efi.cfg`、`board/pc/post-image-efi.sh`、
`boot/grub2/grub2.mk`、`linux/linux.mk` 后修正了三处想当然的写法：

1. **GRUB EFI 产物路径**：Buildroot 已经把 `bootx64.efi` 放在
   `$(BINARIES_DIR)/efi-part/EFI/BOOT/`，且 `-p /EFI/BOOT` 作为前缀——所以
   只要把我们的 `grub.cfg` 覆盖到 `efi-part/EFI/BOOT/grub.cfg` 即可，
   **不需要**自定义 builtin config（已删除 `grub-embedded.cfg`）。
2. **内核镜像位置**：`linux.mk` 会把 `bzImage` 直接装进 `$(BINARIES_DIR)`，
   不需要 post-image 里再去 Linux 构建目录里找。
3. **vfat 目录写入语法**：用 `file EFI { image = "efi-part/EFI" }`（目录）
   而不是在 `files = { }` 里写带斜杠的子路径。
4. **数据分区**：genimage 的 `ext4` 不写 `mountpoint` 的用法在所有官方配置
   里都没有先例，改为在 post-image 里用 host `mke2fs -d` 生成
   `data.ext4`（带卷标 `SHUI-DATA`、预置 `/workspace` 与 `/shuios` 目录），
   genimage 只负责把它塞进分区表。

## V9 · 本地推理接入（llama.cpp + 模型挑选策略）

**为什么是这个方案**：`shui` 的自然语言能力需要一个本地推理后端。
shuios 不自己写推理引擎，而是接 llama.cpp 的 OpenAI 兼容服务——
`shui` 侧只是 POST 一个 `/v1/chat/completions`，与具体引擎解耦。

**落地的三部分**

1. `br2-ext/package/llama-cpp/`：自建 Buildroot 包（上游没有），
   cmake 构建，只产出 `llama-server` / `llama-cli` / `llama-bench` + 共享库。
   源码 tarball 已实际下载并按 **SHA256 校验**：
   `55d67acf…21c5e1`（36.41 MB，GitHub codeload 实测约 1 MB/s）。
2. `shuios-llama.service` + `shuios-llama` 脚本：`ConditionPathExistsGlob`
   保证**没有模型就不启动**（不白占内存）；模型选择调用
   `shui-ctl model-select`，不在脚本里重复实现选择策略。
3. `shuios-proto::models`：模型挑选策略（11 个测试，并入 proto 的 29 个）。

**挑选策略（可解释、可测试）**

| 规则 | 理由 |
| --- | --- |
| 优先 `.gguf` | 只有 gguf 是 llama.cpp 的原生格式，其他格式要先转换 |
| 能装下的里面挑最大的 | 能力随参数量增长，但装不下等于不能用 |
| 需要内存 = 体积 × 1.25 | KV cache + 运行余量的经验系数 |
| 预算 = 可用内存 × 70% | 留 30% 给系统与页缓存 |
| 都装不下就挑最小的 | 宁可慢也要能起来 |
| 同分按名字排序 | 结果确定，可复现 |

**顺手修掉的真 bug**：`shuios-llama.service` 最初写了
`PrivateNetwork=yes` —— 那会把服务放进独立网络命名空间，
`shuiosd`/`shui` 就再也连不上它的 `127.0.0.1:8080`。
"不对外暴露"应该靠服务只 bind 回环地址，而不是靠网络命名空间隔离。

**待真机验证**：llama.cpp 的 CMake 选项名（`LLAMA_BUILD_SERVER` 等）
与产物布局（`bin/llama-server`）需要在实际构建时确认；
包里已加 post-install 校验，产物缺失会明确报错，而不是静默产出坏镜像。

## V11 · 自研开机动画（v0.2 第一件）

**为什么不用 plymouth**：Buildroot 2025.02 里**没有 plymouth 包**（实测目录不存在）。
与其移植，不如自己写一个直接画帧缓冲的小程序——更符合 shuios「少依赖、可控」的路子。

**实现**：`crates/shuios-splash`（Rust，只依赖 libc）
* 几何从 sysfs 读（`/sys/class/graphics/fb0/{virtual_size,stride,bits_per_pixel}`），
  不做 ioctl 结构体对齐，避开 32/64 位布局差异；
* mmap `/dev/fb0` 直接写像素，支持 32bpp；
* 自带 5x7 点阵字体 + 手绘的「氵」字形（两点一提）；
* 画面：竖直渐变背景 + 底部正弦水波 + 中央氵 Logo（带浮动）+ SHUIOS/BOOTING 文字
  + 进度条 + 呼吸点；关机模式显示 SHUTTING DOWN；
* 两个 systemd 单元：`shuios-splash.service`（挂 `sysinit.target`）；
  关机动画则挂在 `shuios-desktop.service` 的 `ExecStopPost=`，
  `shuios-splash-shutdown.service` 只做"桌面没跑时"的兜底（用 `/run/shuios/.splash-done` 去重）；
  桌面启动时 `ExecStartPre=-/usr/bin/pkill -x shuios-splash` 让位。

**验证（QEMU 连续抓帧 + 像素分析）**

| 时刻 | 青色像素（Logo+进度条） | 白色像素（标题） | 灰色（副标题） | 青色包围盒 |
| --- | --- | --- | --- | --- |
| 14 s | 4838 | 5696 | 2725 | x 410..684 |
| 16 s | **5026** | 5696 | 2725 | x 410..**718** |

包围盒右边界变大 = **进度条确实在增长**，说明动画在动而不是静态图。
之后桌面正常接管（截图恢复成 113 色的桌面特征）。

**踩的坑**：第一版逐像素写背景，在 TCG 软件模拟下一帧要好几秒，
抓到的永远只画到渐变、Logo 永远不出现。改成「按行算一个 u32 再 `copy_nonoverlapping`」
之后立刻正常。**结论：帧缓冲绘制必须按行批量写。**

## V12 · 关机动画（v0.2 第二件）

开机动画能看见，关机动画却一直"只有底色"。查下来是两个独立问题叠加：

**问题一：systemd 的停止顺序是启动顺序的反向。**
`shuios-splash-shutdown.service` 写了 `After=shuios-desktop.service`，
本意是"桌面先退场再画关机动画"；但 `After=` 对停止阶段意味着
**这个单元比桌面更早被停掉**，二者其实可以同时在跑。
结果动画在 weston 还占着扫描缓冲时就开始画。

修法：把动画挂到桌面服务的 `ExecStopPost=`。这个钩子保证在
weston 进程树（`KillMode=control-group`）被回收之后再执行。

**问题二（真正让画面空白的）：合成器在的时候，fbcon 的刷屏通道是关的。**
内核在 DRM master 被合成器拿走期间把 fbcon 标记为隐藏（`CON_HIDDEN`），
deferred IO 不再把影子缓冲刷到扫描输出——这时候写 `/dev/fb0` 什么都不会发生。
开机时动画跑在桌面之前，屏幕自然正常；关机时它和 weston 抢同一块扫描输出，
画进去的帧全被留在影子缓冲里，只有等 weston 退出、fbcon 重新可见时，
内核才把**最后一帧**（正好是清屏后的底色）刷出去——这就是我最早截图看到的
"满屏 `#1b2028`、没有 Logo"。

（另：sway 模式下 `shuios-session.sh` 还会显式解绑 vtcon 抢 master，
那时连刷新通道都不存在，需要把 `bind` 写回 1。`shuios-splash` 现在开屏前
会扫 `/sys/class/vtconsole/*/name`，命中 `bind=0` 就绑回来，作为 sway 的兜底。）

**验证（停止桌面触发 `ExecStopPost` → 抓帧 → 数像素）**

| 元素 | 颜色 | 像素 |
| --- | --- | --- |

## V13 · 软件包管理器 `shui-pkg` + 软件商店 `shui-store`

**包格式**：一个 squashfs，自带依赖闭包，装成可写数据分区上的只读挂载点。
打包脚本 `tools/make-pkgrepo.sh` 的做法：单独构建某个包 → 对比
`output/target` 前后差异（含依赖新增的文件）→ 打 squashfs → 把文件挪出 target
（镜像保持干净）。

**实际打出来的包**

| 包 | 版本 | 大小 | 文件数 | 内容 |
| --- | --- | --- | --- | --- |
| `htop` | 3.3.0 | 1.7 MiB | 5 + 2 个 .so | 进程查看器 |
| `libcurl` | 8.16.0 | 2.2 MiB | 150 | curl + libcurl + mbedTLS 3.6.5 + zlib |

**端到端验证（VM 内）**

```text
shui-pkg install htop     → 下载 1777664 字节、校验 SHA-256、挂载、建包装脚本
htop --version            → htop 3.3.0
shui-pkg install libcurl  → curl 8.16.0 ... libcurl/8.16.0 mbedTLS/3.6.5 zlib/1.3.1
                            Protocols: file ftp ftps http https ipfs ipns mqtt
shui-pkg remove htop      → 挂载点消失、包装脚本删除
重启                      → shuios-pkg.service: ✓ libcurl 已恢复（自动重挂）
shui-ctl call pkg.list    → [已装] libcurl / [    ] htop
```

**踩的四个坑**

1. **包内私有库加载不到**：最初用软链把可执行文件指进包内，结果
   `curl: error while loading shared libraries: libcurl.so.4`——包的 `usr/lib`
   不在动态链接器的搜索路径里，而根目录只读、没法写 `ld.so.conf.d`。
   改成**包装脚本**：`LD_LIBRARY_PATH=<包>/usr/lib:<包>/lib exec <包>/usr/bin/<程序> "$@"`。
2. **断链**：用 `cp -a` 拷 `.so` 会连软链一起拷，得到一条指向不存在版本的死链。
   改用 `cp -L`，按 SONAME 落成真文件。
3. **装的东西重启就没了**：`/var/lib/shuios` 当时只绑了 `models` 子目录，
   其余在 tmpfs 上。改成整棵绑定：`/data/shuios → /var/lib/shuios`。
4. **打包脚本自己污染镜像**：`restore_target` 会把上个包的闭包还回 target 以便算差集，
   但结尾只收回"最后一个包"的差异，前面的包就残留在镜像里（表现：
   镜像里莫名出现 `/usr/bin/htop`）。现在结尾按"已知额外文件清单"全量清一次。

**软件商店**：`shui-store` 用 GTK3 + Cairo，37 KB，开机由桌面脚本拉起。
截图里能看到标题栏、搜索框、两张卡片（htop / libcurl）与安装按钮，
窗口底色 `#1b2028`、卡片 `#232a33` 与桌面配色一致。

## V14 · 画面"每一帧都留在屏幕上"（拖影 / 叠帧）

**症状**：在 VM 窗口里拖窗口或移动鼠标时，画面像描图纸一样层层叠加——
指针拖出一条蛇、窗口拖出一叠影子，而且似乎从不清理。

**真正的根因：同时跑了两个 weston。**
Buildroot 的 `weston` 包会把自己挂进 `multi-user.target.wants`，
而我们的 `shuios-runtime` 里那条 `rm -f` 在 weston 之后安装时就白做了。
结果开机后有两个合成器同时开工：

```text
253  weston --log=/run/shuios/weston/compositor.log      ← weston.service，占着 DRM master
267  weston --log=/run/shuios/compositor/compositor.log  ← shuios-desktop.service（MainPID）
     日志：atomic: couldn't commit new state: Permission denied
           repaint-flush failed: Permission denied
```

而且**每个 weston 都拉起了一整套桌面**：2×foot、2×shui-store、2×mc、
2×weston-desktop-shell。两个合成器抢同一块扫描输出，各自按自己的脏区重绘，
画面就变成两边内容的叠加——正好是"每一帧都留在页面上"。CPU 也被吃掉一倍，
weston 日志里全是输入延迟告警：`event processing lagging behind by 106ms`。

**修法**（`board/shuios/x86_64/post-build.sh`，放在 post-build 里是因为它一定
在所有包安装之后执行）：

```sh
rm -f .../multi-user.target.wants/weston.service
ln -sf /dev/null .../etc/systemd/system/weston.service   # mask
```

**顺带**：显示设备从 `-vga std`（bochs，单扫描缓冲）换成 `virtio-gpu`
（整帧翻页），现在是 `tools\run-vm.ps1` 的默认值，`-Bochs` 可回退。

**修好之后的实测证据**

| 检查 | 结果 |
| --- | --- |
| 进程树 | 只有 1 个 sway + 1 个 swaybar + 1 套 foot/store/mc |
| 两次截图（相隔 1 秒） | 近白像素 14960 → 14973，光标始终只有 1 个 16×20 光斑 |
| 脏区动画客户端 | 每帧只有 1 个方块（9600 px），两帧完全相同，没有叠加 |
| sway 下连续两帧 | 变化像素 **0（0.00%）**，537 色 |

**这个 bug 还连带解释了两件事**

1. **sway 一直是"起不来"的**：之前记录的
   `Could not make device fd drm master: Device or resource busy`
   其实是因为 `weston.service` 那个 weston 一直占着 DRM master。
   把重复实例 mask 掉之后，sway 直接就能跑（`drm master` 报错 0 条）。
   现在 **sway 是默认合成器**，任务栏 `swaybar` + `shui-ctl bar` 一并生效。
2. **`shuios-desktop.service` 里的 `RuntimeDirectory=shuios` 是个定时炸弹**：
   `systemctl restart` 桌面时 systemd 会把整个 `/run/shuios` 删掉重建，
   shuiosd 的控制套接字与 MCP 总线**连带被删**（shuiosd 还在跑，但没人连得上，
   `shui-ctl bar` 报 `No such file or directory`）。
   改成 `RuntimeDirectory=shuios/compositor`，并给 shuiosd 加
   `RuntimeDirectoryPreserve=yes`。

**CPU 层面的现实**：VM 只有 TCG 软件模拟（见下面的 WHPX 查证），
所以拖动/动画的帧率仍受限于模拟速度；但"每一帧留在屏幕上"这种
**内容叠加**是合成器实例重复造成的，现在已经没有了。

**WHPX 查证（结论：此版本不可用）**：开 WHPX 时 OVMF 在 `0x829AD9` 抛 `#GP`，
换 `-cpu host` / `-cpu qemu64`、换 `pc`/`q35` 都一样；`smm=on`（WHPX 不支持 SMM）
直接退出。所以 VM 仍是 TCG 软件模拟，CPU 慢是硬伤——只能靠"少画点"优化。

## V16 · 鼠标飘闪 / 区域黑块 / 页面卡顿：三个不同根因（2026-10-27）

用户报的症状是同一句话，实际查出来是**三条互不相关的路径**。全部用像素统计验证，
不靠"看起来好了"。

**测量方法**：QEMU monitor `screendump` 出 PPM → 按区域逐像素 diff。
黑块用"连续 ≥24 px 的纯黑游程"计数，这样时钟文字和光标描边（约 100 px）不会误判。
另外用宿主机截屏（`CopyFromScreen` 抓 QEMU 客户区）交叉验证过：黑块在**宿主机窗口里
也看得见**，不是 screendump 的抓帧竞态。

| 环境 | 根因 | 证据 | 处理 |
| --- | --- | --- | --- |
| VMware（`mks.enable3d = "FALSE"`） | vmwgfx 无 EGL screen，sway 建不出 renderer 直接退出，会话掉到 Weston；Weston 没有 wlr-layer-shell（waybar/Dock 起不来），软件合成留黑块和残影 | 串口：`VMware: No 3D enabled` → `DRI2: failed to create screen` → `Failed to create renderer` → `回退到 Weston` | `run-vmware.ps1` 每次启动前把 `mks.enable3d=TRUE` 钉进 .vmx；`shuios-session.sh` 在非 vmwgfx 上先试 `kms_swrast` 再退 |
| 软件渲染 + blur | swayfx 的 blur 背景纹理在 llvmpipe 上逐帧不稳定，半透明 panel 每帧采到不同底色 | 静置 4 s：blur 开 = 菜单栏 35840 px + Dock 23708 px 全量重绘；blur 关 = 58 px | 轻效档 `blur disable`（`docs/06` 档位表已同步） |
| QEMU virtio-gpu **2D** | 宿主机侧 surface 只收到脏矩形的局部传输，新分配资源的其余部分是黑的；不是 guest 渲染错 | 冷启动后黑块反复出现：8 帧采样最坏 12256 px，64 像素对齐、持续数秒到数分钟；`swaymsg reload`（强制全屏重绘）后 32 帧全 0；同一镜像换 bochs VGA：8 帧 0 黑块，鼠标移出再移回后桌面变化 **0 像素** | `run-vm.ps1` 默认改成 bochs VGA；virtio-gpu 2D 保留 `-Virtio` 只做对照 |

**排除掉的假设**（都实测过，避免后人重走）：

- `WLR_DRM_NO_ATOMIC=1`、`WLR_RENDER_NO_EXPLICIT_SYNC=1`、`WLR_RENDERER=pixman`、
  `WLR_SCENE_DISABLE_VISIBILITY=1` —— 黑块都还在，所以不是 atomic/显式同步/GL/可见性裁剪。
- 黑块跟着指针走？把指针分别停到 `(0,0)`、`(640,400)`、`(1100,700)`，黑块始终只在
  顶部 64 行，不跟随。
- 重新下发壁纸（`output * bg ...`）不能清掉黑块，`reload` 能 —— 说明不是贴图上传，
  而是"新缓冲被当成已有完整内容"。
- `-device virtio-gpu-pci,gl=on` 在本构建不存在（`Property 'virtio-gpu-pci.gl' not found`），
  3D 是独立机型 `virtio-gpu-gl-pci`；而本机 QEMU 11.1 走 virgl 呈现会崩在
  NVIDIA `nvoglv64.dll`（0xc0000005，Windows 应用程序日志可查），所以 `-Gl` 只留作对照。

## V17 · 帧率失控 / 中文 locale / VMware 3D 收尾（2026-10-29）

V16 之后还剩两类问题：**QEMU 下拖动/动画明显卡**（CPU 100%~300%），
以及 **VMware 3D 档没有端到端跑过**。另一个一直没解决的是中文环境
（Buildroot glibc 默认不生成 locale 数据，foot 直接拒绝启动）。这一版全部闭环。

### 1. 卡顿根因：bochs 不按 vblank 节流，帧事件没有上限

QEMU 的 bochs 显卡（`1234:1111`）完成 page flip 不等 vblank：flip 立即返回，
wlroots 收到后立刻给客户端发 frame 事件——客户端画多快就发多快。
实测同一窗口从 176 fps 涨到 334 fps、sway 约 300% CPU（补丁提交说明里的原始测量）。
屏幕只有 75 Hz，多出来的帧都是无用功，还要和输入事件抢 CPU，手感就是"卡"。

补丁：`br2-ext/patches/wlroots/0.20.0/0001-drm-pace-frame-events.patch`
（Buildroot 经 `BR2_GLOBAL_PATCH_DIR` 自动应用，改后 `wlroots` 重编即生效）。

- flip 完成时不再立即 `wlr_output_send_frame`，先记录时间；距上次发帧不足一个
  刷新周期（`1e9/refresh` ns）就用 event-loop timer 延迟发；
- 真 GPU 的 flip 本来就在 vblank 完成 → `delay = 0`，行为不变；
- 只有"立即完成"的驱动（bochs）被夹到屏幕刷新率。

**QEMU（bochs + WHPX，1280×800@75Hz，250×250 `weston-simple-egl`）**

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| 客户端帧率 | 176 → 334 fps（无上限） | 48.4 → 72.4 → 72.2 → 67.8 fps（贴着 75Hz） |
| 拖动/缩放 12 s 内 sway CPU | 无节流，持续满载 | 74%，客户端 2% |
| 空闲 sway | 持续重绘 | **0 ticks/10 s = 0%** |
| 4 s atomic flip / 错误 | — | 262 次 / 0 |
| 顶栏自报 CPU | — | 0.08% |

> 48.4 是第一个 5 秒（窗刚建、字体/壁纸缓存还冷），稳定后 67.8~72.4 fps。
> 帧率不是越高越好，贴着刷新率、CPU 降下来才是正常桌面。

### 2. 中文 locale：Buildroot 默认不带 locale 数据

之前 foot 拒绝启动、GTK 报 `Locale not supported`。根因不是"要重编 glibc"
（NEXT.md 旧说法有误），而是 Buildroot **默认不生成 locale 数据**，连 `C.UTF-8` 都没有。

- `defconfig`：`BR2_GENERATE_LOCALE="zh_CN.UTF-8 en_US.UTF-8 C.UTF-8"`
  → `/usr/lib/locale/locale-archive`
- `post-build.sh`：写 `/etc/locale.conf` 与 `/etc/profile.d/locale.sh`（`LANG=zh_CN.UTF-8`）
- `shuios-session.sh`：`export LANG="${LANG:-zh_CN.UTF-8}"`

实测：`/etc/locale.conf`、登录 shell、sway 会话里的 `LANG` 都是 `zh_CN.UTF-8`；
foot 正常启动并显示中文。

### 3. 默认图形栈收敛

- `shuios-session.sh` 默认合成器是 **swayfx**（旧注释仍写着 weston，已更正）；
  EGL 起不来时：vmwgfx 直接报"宿主机要开 3D"，其他驱动用 `kms_swrast` 重试，
  最后才回退 weston（无任务栏，只保证有画面）。
- `run-vm.ps1` 默认 **bochs VGA**；只有 `virtio_gpu` 驱动开
  `SHUIOS_FORCE_FULL_DAMAGE=1`（全屏重绘换正确性，代价是卡）。
- `run-vmware.ps1` 每次启动前钉 `mks.enable3d = "TRUE"`。

### 4. VMware Workstation 端到端（3D 档）

串口确认 `GPU=vmwgfx → 轻效档（无阴影、无 blur、圆角 6、软件光标）`，
swayfx 正常启动，不再回退 Weston。用 Workstation 自带 VNC
（`RemoteDisplay.vnc.enabled="TRUE"`，5900）抓帧：

| 项 | 结果 |
| --- | --- |
| 桌面 / 壁纸 / 顶栏 / Dock | 正确渲染（1280×800 @60） |
| foot 终端（中文 shui 提示符） | 正常 |
| 软件商店 | 正常 |
| 250×250 `weston-simple-egl`（`LIBGL_ALWAYS_SOFTWARE=1`） | 57.0 / 57.8 / 57.8 fps @60Hz |
| 同场景 sway CPU | 8%（客户端 7%） |
| 静置顶栏自报 CPU | 0.02% |

**VMware 已知限制**

- 硬件缓冲的 EGL 客户端在 vmwgfx 上失败：
  `[destroyed object]: error 7: importing the supplied dmabufs failed`。
  软件 GL（`LIBGL_ALWAYS_SOFTWARE=1`）和 shm 客户端（GTK、foot）都正常，
  系统自身绘制不受影响。
- Workstation 17 自带 VNC 服务器**只出画面、不收输入**：实测 RFB PointerEvent
  发到 (800,400) 后截图里光标仍停在 (102,104)。VMware 下的拖动/点击需人工鼠标；
  拖动链路的自动化证据来自 QEMU QMP 绝对坐标注入（同一套合成器输入路径）。

**测量工具**（`.cache/`，可复现）：`vnc-grab.mjs`（RFB 3.8 + Raw 截图 → PNG，
不依赖 VMware Tools）、`qmp-drag.ps1`（QMP `input-send-event` 拖动）、

### 3. 下载失败的真根因（两处，必须同时修）

1. **没有把"不支持的响应"转成下载。** WebKitGTK 不会自动下载任意非 HTML
   主资源；MiniBrowser 在 `decide-policy` 的 RESPONSE 决策里调用
   `webkit_policy_decision_download()`。外壳最初漏了这一步，
   `https://httpbin.org/bytes/1024` 只是被当成渲染失败的页面。
2. **错误页取消了刚发起的下载。** 转下载时 WebKit 先以
   `Frame load interrupted by policy change`（`WEBKIT_POLICY_ERROR_..._102`）
   结束当前加载，它比 `download-started` 更早到达。`load-failed` 里原先
   加载错误 HTML，等于把 pending 的下载取消。修法：`Cancelled` 与
   `FrameLoadInterruptedByPolicyChange` 都直接忽略。

另外 WebKit2GTK 4.1 **没有** `webkit_download_get_suggested_filename()`
（那是 6.0 / `WebKitNetworkSession` 的 API）。文件名要从
`webkit_download_get_response()` + `webkit_uri_response_get_suggested_filename()`
取，取不到再取 URL 路径 basename（URL 解码），最后兜底 `download.bin`。

### 1. 交付内容

| 能力 | 实现 |
| --- | --- |
| 锁屏 `shui-lock` | GTK3 + gtk-layer-shell：namespace `shui-lock`、layer **OVERLAY**、四边锚定、`exclusive_zone=-1`、键盘 **EXCLUSIVE**。暗化壁纸 + 时钟/日期 + 用户卡片 + 密码框 + 解锁按钮 + 右下重启/关机 |

| 防绕过 | 锁定时切到 sway binding mode `shui-lock`：默认 `Win+*` 绑定全部失效；解锁或异常退出恢复 `default` |
| 看门狗 | shui-idle 每 500 ms 检查 `/run/shuios/lock.pid`；锁进程异常消失 → 删 pidfile + `mode default`，重新计时后再次锁定 |

| 测试注入 `shui-key` | Wayland `zwp_virtual_keyboard_manager_v1`：`--text` / `--combo logo+l` / `--key`，供 VNC 只读环境下的自动化验收 |

### 2. 实现要点

- **整屏覆盖用 `exclusive_zone=-1`**：layer-shell 的 -1 才是「使用整块输出」；
  写 0 会进入非独占排列，被任务栏的 `exclusive_zone=40` 裁成 1280×760，底部
  露出任务栏（踩过）。
- **键盘独占 + binding mode 双保险**：EXCLUSIVE 让按键不进入任何客户端；
  `mode "shui-lock"` 让 sway 不执行默认绑定。实测锁定中注入 `Win+Return`
  不会弹出终端。
- **鉴权放在锁屏进程内**：桌面本身是 systemd system service（root），锁屏可以
  直接读 `/etc/shadow`；镜像没有 PAM（无 `/etc/pam.d`），因此用 `crypt_r()`
  而不是 `pam_authenticate()`。
- **单实例**：`flock(/run/shuios/lock.lock)` + `/run/shuios/lock.pid`；重复启动
  直接退出；PID 文件同时给看门狗与测试脚本用。
- **信号**：SIGTERM/SIGINT/SIGHUP 都走正常解锁路径（恢复 `mode default`、
  删 pidfile、释放锁），避免 systemd 停会话时留下锁死状态。
- **虚拟键盘必须自己发 modifiers**：wlroots 0.20 的
  `zwp_virtual_keyboard_v1.key` 带 `update_state=false`，合成器不会从按键推导
  修饰键；每发一个键后都要 `zwp_virtual_keyboard_v1_modifiers(depressed,
  latched, locked, group)`，否则 `Super` 等于没按下（踩过：Win+L 注入无反应）。
- **错误提示的显示顺序**：先 `gtk_entry_set_text("")` 再显示错误；反过来清空
  输入会触发 `changed` → `hide_error`，刚显示的错误提示会立刻被藏掉（踩过）。
- **锁屏不接输入法**：会话里 `GTK_IM_MODULE=fcitx`，fcitx 在中文态会把物理
  按键吃进 preedit、把 Enter 当候选提交，密码可能根本到不了输入框。锁屏在
  `gtk_init` 后强制 `gtk-im-module=gtk-im-context-simple`，只用 GTK 内置
  simple IM。合成虚拟键盘走 Wayland 协议、不经过 fcitx，所以自动化验收
  发现不了这一类问题——这是为宿主真实键盘补的防御。

### 5. 限制

- swayfx 0.6 **没有 `ext-session-lock`**：锁屏是 layer OVERLAY + 键盘独占 +
  binding mode 的组合，不是合成器级安全锁。理论上其它客户端仍可再建一个
  OVERLAY surface 盖住锁屏；也没有「锁屏时禁止截屏/输入捕获」的协议保证。
- 锁屏以 **root** 运行（桌面本身是 system service）；没有独立登录管理
  （PAM/greetd/logind session lock），“注销”只是重启 sway 会话。
- 密码尝试**没有限速/锁定**，也不支持指纹/USB 令牌；错误提示不显示剩余次数。
- 没有 DPMS 关屏、挂起、休眠、合盖处理：锁定后显示器不会自动熄灭。
- 电源按钮的二次确认只防误触；本地 root 仍可直接 `systemctl poweroff`。
- VMware 宿主真实键盘/鼠标未验证（VNC 只读）；验收输入全部是合成虚拟键盘
  与合成指针。合成键盘走 Wayland 协议、不经过 evdev，所以注入按键不会重置
  空闲计时（测试空闲锁定反而方便）。
- VMware 没有合盖/电池事件；休眠需要 swap + 电源管理配置，当前镜像未做。

  `TempDir` 的 RAII 在调用结束（含失败）时删除文件。
- **端点校验**：远程端点必须是 `https://`，只允许本机回环
  （`127.0.0.1` / `localhost` / `::1`）使用 `http://`；拒绝带用户名密码、
  查询串、片段或空白字符的地址。错误在 `ai.configure` 就返回，不会
  等到请求时才炸。
- **配置语义**：`ai.configure` 只更新传入的字段；`api_key` 不接受空串
  （要删除必须显式 `clear_key:true`）；保存前调用 `AiConfig::validate()`，
  然后原子写入 0600。`ai.status` 只回显 `key_set` 与 `key_hint()`（末四位），
  `config.get` 同样脱敏。
- **`ai.chat` 边界**：messages 最多 200 条 / 512 KiB，temperature 0–2，
  max_tokens 1–32768；远程无密钥直接返回可操作的错误文案（设置 → AI 或
  `shui-ctl ai set --key-stdin`）。请求与回复都不落盘。
- **`ai.test`**：固定中文探活提示，temperature 0、max_tokens 16、超时
  5–30 s；失败也返回 `ok:false` 的 JSON（含错误文本），供 GUI 展示，
  而不是当成 RPC 异常。
- **GUI 保存密钥**：输入框为密码模式；点击保存时把内容写进 0600 临时
  文件，调用 `shui-ctl ai set --key-file`，随即 unlink；界面从不回读密钥。
- **GUI 测试线程**：`ai.test` 在 GThread 里跑，结束后必须
  `g_idle_add()` 回主循环更新控件；只在工作线程里 return 会让按钮永远停在
  “正在连接推理服务…”。
- **导航换回 `row-activated`**：V26 用 `row-selected` 响应导航，Tab 经过
  侧栏行就会切页，焦点被困在导航里、进不了右侧表单；V27 改为单击/回车
  才切页（见 §3）。

### 5. 限制

- **没有真实远程提供商的一次成功对话**：需要用户提供密钥；已证明到
  TLS/CA 与 401（鉴权失败是服务端给的，说明请求到达了服务商）。
- 本地推理未随镜像验证：模型仓库里没有 `.gguf`，`shuios-llama` 自动选型
  与启动链路仍未实测。
- 只有一次性 chat：没有流式输出、取消、多轮会话持久化；`shui` 每次
  运行是独立会话。
- 没有远程模型列表：模型名手填，`/models` 未接；设置页也不暴露
  timeout / temperature（只能用 `shui-ctl ai set`）。
- 密钥是 0600 明文文件，没有系统密钥环/加密；shuiosd 以 root 运行。
- 未接代理与自定义 CA；证书验证完全依赖系统 CA bundle。
- AI 运行时 v1 的其余部分未开始：Landlock/seccomp、授权 UI、审计、
  模型管理、RAG、多智能体。

## 已知小瑕疵（不影响使用）

- foot 的 CSD 标题栏是 GTK 默认浅灰，和任务栏的深色扁平风格不完全一致（纯外观）
- sway 光标用内置默认主题，没有 `dnd-move` 抓取光标（拖动时指针不变形）
- xkb 缺 Compose 文件（死键不可用）
- fontconfig 警告 `44-wqy-zenhei.conf: multiple values in <test>`（无害）
- 全屏 1280×800 软件渲染客户端在 QEMU 下约 37 fps（llvmpipe 极限，不是合成器问题）
- A/B 升级端到端未验证（见上）
- vmwgfx 硬件缓冲 EGL 客户端不可用（见 V17；软件 GL + shm 客户端可用）
- WebKit 沙箱不可用（镜像无 `bwrap`）；下载无历史/取消（见 V18 限制）
- PipeWire 只覆盖默认输出设备：没有设备切换/麦克风/单应用音量，也没有托盘
  音量弹层；音量持久化只覆盖我们 UI 发起的修改（见 V26 限制）
- 任务栏没有窗口缩略图/分组；右键直接关窗，没有上下文菜单；开始菜单裸 Win
  键未绑定（`Super+D`）；任务栏动作暂无 MCP（见 V24 限制）
- 锁屏密码没有尝试限速/锁定；锁定后不关屏；电源按钮防误触只有 3 s 二次确认
- 锁屏本身以 root 运行且无 PAM/独立登录会话（桌面是 system service，见 V25 限制）
- AI 只有一次性 chat：无流式/取消/多轮持久化；无远程模型列表；设置页不暴露
  timeout/temperature；密钥是 0600 明文、无系统密钥环（见 V27 限制）
