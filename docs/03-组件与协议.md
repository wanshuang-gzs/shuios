# 组件与协议

## 1. 控制平面协议

Unix 套接字 `/run/shuios/shuiosd.sock`，**JSON Lines**：一行一个 JSON 对象。
没有握手、没有版本协商字段——先查 `version` 方法即可。

### 1.1 信封

请求：

```json
{ "id": "c1", "method": "agent.list", "params": {} }
```

响应（成功）：

```json
{ "id": "c1", "result": [...] }
```

响应（失败）：

```json
{ "id": "c1", "error": { "code": -32001, "message": "智能体 foo 不存在" } }
```

同一连接上可以连续发多个请求，按序返回（`shui`/`shui-ctl` 都是这么用的）。

### 1.2 方法表

| 方法 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `ping` | – | `{pong, version, protocol}` | 探活 |
| `version` | – | `{name, version, protocol, codename}` | 版本 |
| `config.get` | – | `Config` | 守护进程当前配置 |
| `system.info` | – | `SystemInfo` | 主机名、内核、内存、负载、只读根状态 |
| `agent.spawn` | `AgentSpec` | `AgentInfo` | 派生智能体 |
| `agent.list` | – | `[AgentInfo]` | 列出全部 |
| `agent.get` | `{name}` | `AgentInfo` | 单个 |
| `agent.kill` | `{name}` | `AgentInfo` | 整组击杀并等待退出 |
| `agent.forget` | `{name}` | `{removed}` | 从登记表移除（不杀进程） |
| `agent.logs` | `{name, lines?}` | `[string]` | 内存环形缓冲里的日志尾部 |
| `agent.send` | `{name, data}` | `{sent}` | 向 stdin 写一行 |
| `model.list` | – | `[ModelInfo]` | 扫模型仓库 |
| `ai.status` | – | `AiStatus` | 提供商、端点、模型、是否已配置密钥（不回传密钥） |
| `ai.providers` | – | `[AiProvider]` | 内置提供商预设 |
| `ai.configure` | `{provider?, endpoint?, model?, api_key?, clear_key?, timeout_secs?, temperature?}` | `{saved, status}` | 更新运行时 AI 配置 |
| `ai.chat` | `{messages, model?, temperature?, max_tokens?}` | `{content, model, usage, elapsed_ms}` | 由守护进程代发 `chat/completions` |
| `ai.test` | – | `{ok, reply?, error?, model, endpoint, latency_ms}` | 探活；失败也走成功响应，便于 GUI 展示 |
| `mcp.tools` | – | `[ToolInfo]` | 内置工具清单 |
| `mcp.call` | `{tool, arguments}` | `ToolResult` | 调用内置工具 |

错误码：

| 码 | 含义 |
| --- | --- |
| -32600 | 请求不是合法 JSON |
| -32601 | 方法不存在 |
| -32602 | 参数不合法 |
| -32603 | 内部错误 |
| -32001 | 智能体不存在 |
| -32002 | 智能体已存在 |
| -32003 | cgroup 不可用 |
| -32004 | AI 未就绪（远程提供商未配置 API 密钥） |

### 1.3 数据结构

```jsonc
// AgentSpec —— 派生的输入
{
  "name": "worker",            // [A-Za-z0-9._-]{1,64}
  "argv": ["/usr/bin/sleep", "300"],
  "workdir": "/workspace",     // 可选
  "env": { "FOO": "bar" },     // 可选
  "limits": {                  // 省略则用全局默认
    "memory_max": "2G",        // 支持 K/M/G/T 后缀或 "max"
    "pids_max": 512,
    "cpu_weight": 100,         // 1..10000 → cgroup cpu.weight
    "io_weight": 100           // 1..1000
  },
  "capabilities": ["fs_read", "net"],  // v0.1 仅记录与审计
  "restart": false,
  "description": "示例"
}

// AgentInfo —— 运行视图
{
  "name": "worker", "pid": 1234,
  "state": "running",          // starting | running | exited | failed
  "started_at": 1730000000,
  "exit_code": null,
  "memory_bytes": 1048576,     // 来自 memory.current
  "cpu_usage_usec": 12345,     // 来自 cpu.stat usage_usec
  "limits": { ... }, "capabilities": [ ... ],
  "restart": false, "description": "示例",
  "log_path": "/var/log/shuios/agents/worker.log"
}
```

## 2. cgroup 映射

| shuios 概念 | cgroup v2 文件 | 备注 |
| --- | --- | --- |
| `limits.memory_max` | `memory.max` | 同时写 `memory.swap.max=0`，避免 OOM 时靠 swap 拖死 |
| `limits.pids_max` | `pids.max` | 防 fork 炸弹 |
| `limits.cpu_weight` | `cpu.weight` | 相对权重，不是硬配额 |
| `limits.io_weight` | `io.weight` | `default N` |
| 击杀 | `cgroup.kill` | 内核 5.14+；失败退化为 `SIGKILL` 进程组 |

cgroup 路径：`/sys/fs/cgroup/shuios/<name>/`。
`cgroup v2 不可用` 时所有限额静默跳过，`system.info` 的 `cgroup_v2` 会是 `false`。

## 3. 内置 MCP 工具

| 工具 | 参数 | 权限 |
| --- | --- | --- |
| `sys.info` | – | 只读 |
| `fs.list` | `path` | 只读 |
| `fs.read` | `path`, `max_bytes` | 只读 |
| `fs.write` | `path`, `content` | **白名单**：`/tmp` `/var/tmp` `/workspace` `/var/lib/shuios` `/run/shuios` |
| `proc.list` | – | 只读（`/proc`） |
| `agent.list` | – | 只读 |
| `agent.spawn` | `name`, `command` | 受 `max_agents`、cgroup 限额约束 |
| `agent.kill` | `name` | 整组击杀 |
| `model.list` | – | 只读 |

模型侧的调用协议（写进 system prompt）：

```json
{"tool":"fs.read","arguments":{"path":"/workspace/README.md"}}
```

`shui` 每轮最多接受 6 次工具调用，防止模型陷入循环。

## 4. 配置文件 `/etc/shuios/shuios.json`

```jsonc
{
  "socket": "/run/shuios/shuiosd.sock",
  "default_limits": { "memory_max": "2G", "pids_max": 512, "cpu_weight": 100 },
  "autostart": [ /* AgentSpec 数组，开机自动派生 */ ],
  "llm": {
    // 只作为首次启动默认值；运行时配置在
    // /var/lib/shuios/state/ai.json（0600，由 shuiosd 管理，见 §9.4）
    "endpoint": "http://127.0.0.1:8080",
    "model": "local",
    "api_key": null,                      // 不参与序列化，config.get 不回显
    "timeout_secs": 180,
    "temperature": 0.2
  },
  "agent_log_dir": "/var/log/shuios/agents",
  "model_dir": "/var/lib/shuios/models",
  "state_dir": "/var/lib/shuios",
  "mcp_tools": true,
  "max_agents": 64,
  "allow_nested_spawn": false
}
```

文件不存在时使用内置默认值（不会报错）。改完需要 `systemctl restart shuiosd`
（注意：根文件系统只读，实际要改的是 `/var/lib/shuios` 下的副本或重新构建镜像）。

## 5. shui 的输入三段论

| 前缀 | 处理 | 是否经过模型 |
| --- | --- | --- |
| `/help` `/sys` `/spawn` … | 内置命令 | 否 |
| `!cmd` 或 `$cmd` | `/bin/sh -c` | 否 |
| 其它 | 自然语言 → 工具循环 | 是 |

内置命令全表见 `shui` 里 `/help` 的输出，或 `crates/shui/src/main.rs` 的 `HELP` 常量。

## 6. shui-ctl 子命令

```
status sys agents spawn kill forget logs send tools mcp call models config ping version
ai status|providers|set|test|clear-key
```

`ai set` 的密钥只从 stdin（`--key-stdin`）或 0600 文件（`--key-file`）
读取，不接受命令行明文参数。

设计约定：**输出稳定、无颜色、无交互**，错误走 stderr 且退出码非零。
可以直接 `shui-ctl call fs.list '{"path":"/tmp"}' | grep foo`。

## 7. MCP 系统级总线

shuios 有两套本地 IPC，职责严格分开：

| | 控制平面 | MCP 总线 |
| --- | --- | --- |
| 路径 | `/run/shuios/shuiosd.sock` | `/run/shuios/mcp/system.sock` |
| 协议 | 我们的 JSON Lines 信封 | 标准 JSON-RPC 2.0 + MCP 方法 |
| 面向 | `shui` / `shui-ctl`（受信任的本地工具） | 任意 MCP 客户端（模型/智能体） |
| 能力 | 全部（派生、击杀、日志、配置） | **只有**工具发现与调用 |

**为什么这么分**：模型能用什么由系统决定，不由提示词决定。即使有人把
恶意提示词塞进模型，它能调用的也只是总线上的那几个工具。

支持的方法：

| 方法 | 说明 |
| --- | --- |
| `initialize` | 返回 `protocolVersion`（`2024-11-05`）、`capabilities.tools`、`serverInfo` |
| `ping` | 空对象 |
| `tools/list` | 返回 `[{name, description, inputSchema}]` |
| `tools/call` | `{name, arguments}` → `{content:[{type:"text",text}], isError}` |
| `notifications/*` | 通知（无 `id`），收到即丢、不回包 |

示例（一行一个 JSON，按行分隔）：

```jsonc
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"fs.list","arguments":{"path":"/workspace"}}}
```

注意 MCP 的约定：**工具执行失败是正常响应 + `isError:true`**，
只有协议层错误（未知方法、参数不是 JSON）才走 JSON-RPC `error`。

## 8. A/B 原子升级

状态存在 ESP 上的 `grubenv`（**恰好 1024 字节**，GRUB 的 `load_env`/`save_env`
读写的就是它），只有三个变量：

| 变量 | 含义 |
| --- | --- |
| `shuios_slot` | 下次要启动的槽（`a` / `b`） |
| `shuios_prev` | 上次**确认成功**的槽 |
| `shuios_state` | `ok` / `try` / `booting` |

状态机（不需要计数器，只靠三值状态）：

```
                 shuios-update apply
   ok  ──────────────────────────────►  try
    ▲                                     │ GRUB 启动时读改写
    │                                     ▼
    │                                booting
    │                                     │
    │   shuios-boot-ok 服务成功            │ 开机后没等到 boot-ok
    └─────────────────────────────────────┴──► 自动回滚到 prev（→ ok）
```

一次升级的完整时序：

1. `shuios-update apply rootfs.squashfs`：校验容量 → 写入**非活动**槽 → 刷盘
   → 写 grubenv（`slot=目标`、`prev=当前`、`state=try`）
2. 重启：GRUB 看到 `try`，把状态改成 `booting` 并启动新槽
3. 新系统到达 multi-user 后，`shuios-bootok.service` 执行
   `shuios-update mark-boot-ok`，把 `state` 改成 `ok`、`prev` 指向当前槽
4. 如果第 3 步没发生（内核 panic、systemd 卡住、总线起不来），下次开机
   GRUB 看到 `booting` 就判定"上次没成功"，自动回滚到 `prev`

手动操作：

```bash
shuios-update status      # 当前槽、grubenv 状态、四个分区的容量
shuios-update slots       # 只看分区
shuios-update rollback    # 立刻回滚
```

**已知约束**：升级命令必须在系统正常运行时执行（它要写非活动槽）；
`squashfs` 大小不能超过槽容量（`post-image.sh` 建镜像时会按实际大小校验）。

## 9. 推理服务、远程提供商与模型挑选

shuios 不自己实现推理引擎：本地走 llama.cpp 的 OpenAI 兼容服务，远程走
任何 OpenAI 兼容提供商（DeepSeek / 通义千问 / Moonshot / OpenAI / 自定义）。
`shui` 只把 messages 交给 `shuiosd` 的 `ai.chat`，由守护进程选择端点并
代发 `POST /chat/completions`——客户端不接触密钥，也不关心换的是哪个引擎。

### 9.1 服务

| 项 | 值 |
| --- | --- |
| 服务单元 | `shuios-llama.service` |
| 启动条件 | `/var/lib/shuios/models/*.gguf` 至少存在一个（`ConditionPathExistsGlob`） |
| 监听 | `127.0.0.1:8080`（只 bind 回环） |
| 可调环境变量 | `SHUIOS_LLAMA_PORT` / `SHUIOS_LLAMA_CTX` / `SHUIOS_LLAMA_THREADS` |
| 模型来源 | `shui-ctl model-select` → `shuiosd` 的 `model.select` |

**没有模型就不启动**是刻意的：空转的推理服务会白占内存与端口，
而 shuios 面向的机器往往只有几 GB 内存。

### 9.2 挑选策略（`shuios-proto::models`）

"该用哪个本地模型"是系统行为，不是让用户每次手填路径。规则：

| 规则 | 理由 |
| --- | --- |
| 优先 `.gguf` | 只有 gguf 是 llama.cpp 原生格式 |
| 能装下的里面挑最大的 | 能力随参数量增长，但装不下等于不能用 |
| 需要内存 = 体积 × 1.25 | KV cache + 运行余量 |
| 预算 = 可用内存 × 70% | 留 30% 给系统与页缓存 |
| 都装不下就挑最小的 | 宁可慢也要能起来 |
| 同分按名字排序 | 结果确定、可复现 |

对应 RPC：

```jsonc
// model.select
{ "selected": {"name":"qwen2.5-3b-q4.gguf","path":"/var/lib/shuios/models/qwen2.5-3b-q4.gguf","size_bytes":2013265920},
  "reason": "选择 qwen2.5-3b-q4.gguf（1.9 GiB，预计需要 2400 MiB，可用 3900 MiB）",
  "count": 2, "available_bytes": 4089446400, "budget_bytes": 2862612480 }
```

`shui-ctl model-select` 只打印路径（单行、无颜色），便于脚本与 systemd 使用：

```bash
MODEL=$(shui-ctl model-select) || exit 1
```

### 9.3 放模型

```bash
ls /var/lib/shuios/models/        # 模型仓库是持久化的（绑定到数据分区）
systemctl restart shuios-llama    # 放入任意 .gguf 后重启推理服务
```

`shui` 启动时通过 `ai.status` 读运行时配置，所以端口用
`shui-ctl ai set --endpoint http://127.0.0.1:9090` 改即可，两边不会漂移。
`/etc/shuios/shuios.json` 的 `llm` 段只提供首次启动默认值；一旦
`/var/lib/shuios/state/ai.json` 存在，就以它为准。

### 9.4 远程提供商与 API 密钥（V27）

| 项 | 值 |
| --- | --- |
| 运行时配置 | `/var/lib/shuios/state/ai.json`（0600，原子写入；权限过宽会收紧） |
| 本地默认 | provider=local，endpoint=`http://127.0.0.1:8080`，不需要密钥 |
| 远程要求 | 端点必须 `https://`；只有 `127.0.0.1` / `localhost` / `::1` 允许 `http://` |
| 预设 | deepseek、qwen（DashScope 兼容模式）、moonshot、openai、custom |
| 传输 | 镜像内 `/usr/bin/curl`（OpenSSL + `ca-certificates`）；Rust 侧不带 TLS 栈 |
| 密钥路径 | `shui`/设置中心 → `shuiosd` → 0600 临时请求头文件 → curl；不经过 argv |
| 回读 | `ai.status` 只给 `key_set` 与末四位 `key_hint()`；`config.get` 同样脱敏 |
| 测试 | `ai.test` 发一次固定探活请求（temperature 0、max_tokens 16、超时 5–30 s） |

安全边界：密钥文件只允许 root 读写；守护进程以 root 运行，日志只记录提示位
（如 `key=…7c21`）；临时请求头/请求体放在 0700 临时目录的 0600 文件里，
调用结束即删除。当前没有系统密钥环或静态加密，这是已知限制。

## 10. 软件包管理器 `shui-pkg`

**为什么不是 apt**：系统本体是只读 squashfs，A/B 双槽保证升级原子性。
往 `/usr` 里写东西会破坏这两条前提。所以包被装成**可写数据分区上的
只读 squashfs 挂载点**，卸载就是把挂载点摘掉。

### 10.1 布局

| 路径 | 作用 |
| --- | --- |
| `/usr/share/shuios/pkgrepo/` | 镜像内置仓库（`index.json` + `*.sqfs` + `icons/`），离线可用 |
| `/etc/shuios/pkgrepo.conf` | `repo = ...`，可改成内网 HTTP 仓库 |
| `/var/lib/shuios/pkg/cache/` | 下载下来的包文件（校验后缓存） |
| `/var/lib/shuios/pkg/mnt/<名>` | 每个包的挂载点 |
| `/var/lib/shuios/pkg/bin/` | 可执行文件软链（已在 `PATH` 里） |
| `/var/lib/shuios/pkg/share/applications/` | 桌面入口软链（在 `XDG_DATA_DIRS` 里） |
| `/var/lib/shuios/pkg/installed.json` | 已装清单，开机由 `shuios-pkg.service` 重建 |

### 10.2 包格式

一个包 = 一个 squashfs，根目录带 `.pkg/meta.json`：

```json
{ "name": "htop", "version": "3.3.0",
  "bins": ["usr/bin/htop"],
  "desktop": [] }
```

**每个包自带依赖闭包**：打包时把「这个包 + 它递归依赖新增的全部文件」
一起塞进去（`tools/make-pkgrepo.sh` 用 `output/target` 的前后差异算）。
所以 `libcurl` 包 150 个文件里，大头是 mbedtls 的库——装上就能直接抓 HTTPS。
代价是磁盘占用略高，换来的是**任何两个包都不会互相破坏**。

### 10.3 命令

```bash
shui-pkg list [关键字]     # 仓库清单（--tsv 给 GUI 用）
shui-pkg info htop        # 详情：版本/体积/SHA-256/依赖/是否已装
shui-pkg install htop     # 安装（自动解析依赖，落盘前校验 SHA-256）
shui-pkg remove htop      # 卸载（摘挂载、删软链与包文件）
shui-pkg installed        # 已装清单
shui-pkg update           # 刷新索引缓存（远程仓库）
shui-pkg restore          # 开机钩子：按清单重建挂载与软链
shui-pkg repo             # 仓库位置与连通性
```

校验和是**自己实现的 SHA-256**（`crates/shui-pkg/src/sha256.rs`，带 FIPS 官方
测试向量）；HTTP 也只是最小 GET 客户端——镜像里不塞 TLS 库，所以只支持
`http://`，要 HTTPS 就在前面架反向代理。

### 10.4 MCP 工具（智能体视角）

智能体和人是同一套能力，只是入口不同：

| 工具 | 作用 |
| --- | --- |
| `pkg.list` | 列出可安装的包（带 `[已装]` 标记） |
| `pkg.installed` | 已装清单与挂载点 |
| `pkg.install` | 安装（真的写盘；包名做白名单校验后调 `shui-pkg`） |
| `pkg.remove` | 卸载 |

```bash
shui-ctl call pkg.list '{}'
shui-ctl call pkg.install '{"name":"htop"}'
```

## 11. 软件商店 `shui-store`

`shui-store` 是自研的 GTK3 图形界面（`br2-ext/package/shui-store/src/shui-store.c`）：

* 读 `shui-pkg list --tsv` 的制表符清单——**GUI 里不解析 JSON**，
  解析交给 Rust 侧，界面只消费已经拍平的数据；
* 图标用 **Cairo 现画**（圆角底板 + 包名首字母，颜色按包名哈希取），
  不依赖图标主题或图片资源，因此换主题不会出现空白图标；
* 点「安装/卸载」就 `shui-pkg install|remove <包名>`，跑完自动刷新。

为什么不用现成的文件管理器/应用商店：Buildroot 里的 `pcmanfm`、`leafpad`
都硬依赖 `BR2_PACKAGE_XORG7`，而 shuios 是纯 Wayland，没有 X11。
自己写一个 GTK3 小应用反而是最省依赖的路子（编译进去只有 37 KB）。




## 12. 输入法（fcitx5 + Rime）

组件（Buildroot 包，`br2-ext/package/` 之外的上游包里选型）：

| 组件 | 版本 | 作用 |
| --- | --- | --- |
| `fcitx5` | 5.1.23 | 输入法框架；`waylandim` 前端 + `classicui` 候选窗 + D-Bus 前端 |
| `fcitx5-gtk` | 5.1.7 | GTK3 immodule（`im-fcitx5.so`），GTK 应用走 D-Bus 直连 |
| `fcitx5-rime` / `librime` | 5.1.16 / 1.17.0 | Rime 引擎 |
| `rime-data` | — | 朙月拼音·简化字（`luna_pinyin_simp`） |

三条输入链路：

```
foot / 原生 Wayland 客户端
   键盘事件 → 合成器(sway) → zwp_text_input_v3 → zwp_input_method_v2 → fcitx5

GTK3 应用（含 shui-browser）——两种情况
   a) GTK_IM_MODULE=fcitx 且 immodule 可用：键盘事件 → im-fcitx5.so → D-Bus → fcitx5
   b) immodule 不可用：GTK 回退到 Wayland text-input-v3（同第一条）
```

Rime 在此之上再走 `fcitx5-rime` 引擎；候选窗由 `classicui` 作为一个 Wayland
surface 显示（GTK 客户端用客户端候选窗）。

### 12.1 会话侧约定

* **HOME 必须存在**：`fcitx5` 的 `src/server/main.cpp` 在 `HOME` 为空时直接
  打印 `Please set HOME.` 退出。`shuios-desktop.service` 是 system 服务，
  systemd 不注入 `HOME`，`/root` 又只读，所以 `shuios-session` 显式
  `export HOME=/var/lib/shuios/home`。
* **可写目录**：`XDG_CONFIG_HOME=/var/lib/shuios/config`、
  `XDG_DATA_HOME=/var/lib/shuios/data`（Rime 部署词典要写盘）。
* **出厂配置**（只首次灌入，之后用户改的不覆盖）：
  * `/usr/share/shuios/fcitx5/profile` → `DefaultIM=rime`；
  * `/usr/share/shuios/fcitx5/config` → `[Behavior] ActiveByDefault=True`；
  * `/usr/share/shuios/fcitx5/default.custom.yaml` → Rime 简化字方案。
* **immodule cache**：Buildroot 不跑 `gtk-query-immodules`，根分区没有
  GTK 默认的 `immodules.cache`，镜像里手写了 `/etc/shuios/gtk-immodules.cache`
  并由 `GTK_IM_MODULE_FILE` 指定。

### 12.2 为什么默认激活

fcitx5 的 `ActiveByDefault` 没有显式默认值，bool 取 `false`
（`src/lib/fcitx/globalconfig.cpp`），新建的输入上下文一律从 `keyboard-us`
开始，用户必须先按 Ctrl+Space 才能打中文。对中文发行版这是错的默认值，
所以出厂 `config` 把它设为 `True`；`fcitx5-remote` 在聚焦的上下文里应报
`state=2, im=rime`。

### 12.3 验收工具

`tools/ime-test/`（交叉编译后 scp 进 VM，宿主机侧 `ime-verify.sh` 驱动）：

* `vkbd-inject`：`zwp_virtual_keyboard_v1` 注入按键（VMware 自带 VNC 只读，
  收不到输入）。注意 keymap 参数顺序是 `(format, fd, size)`，且字母键位
  不连续；
* `gtk-ime-test`：GTK3 `GtkEntry`，验证 immodule + D-Bus 链路；
* `ime-remote.sh text`：foot 与 GTK 两条链自动判定（期望 UTF-8 `你好`）；
* `ime-evidence.sh`：终端 + 浏览器同屏取证，浏览器起窗口后等 40 s 再注入。

合成键盘没有真实指针点击，WebKit 窗口从映射到"可编辑焦点 → UI 进程输入法
过滤器就绪"需要几十秒；注入太早按键会绕过输入法直落拉丁。验收时等窗口
聚焦后再注入。

## 13. 网络管理（NetworkManager）

组件（全部来自 Buildroot 上游包）：

| 组件 | 版本 | 作用 |
| --- | --- | --- |
| `network-manager` | 1.50.2 | 统一管理有线/无线；`nmcli` 命令行（TUI 未启用） |
| `wpa_supplicant` | 2.11 | WPA2/WPA3 关联（nl80211 + D-Bus） |
| `iw` / `wireless-regdb` / `rfkill` | — | 空口查询、监管域、无线开关 |
| `hostapd` | 2.11 | 仅用于无硬件验证：把虚拟无线电变成 AP |
| `systemd-resolved` | 257 | DNS：stub 模式（`127.0.0.53`），保留 DNSSEC/DoT 能力 |

关键布局：

```
/etc/NetworkManager/system-connections -> /var/lib/shuios/NetworkManager/system-connections
                                          └─ /data/shuios/...（ext4 数据分区，重启保留）
/etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
/etc/systemd/system-preset/00-shuios.preset   # disable networkd / network.service
```

设计决定：

* **用 NM 取代 systemd-networkd**，一套后端同时覆盖有线和 Wi-Fi，后续
  `shui-settings` 直接通过 nmcli/D-Bus 操作。defconfig 里显式
  `# BR2_PACKAGE_SYSTEMD_NETWORKD is not set`——systemd 下它默认是 y。
* **连接配置放数据分区**：根分区是只读 squashfs、`/var` 是 tmpfs，
  只有 `/data`（LABEL=SHUI-DATA）持久。`shuios-storage.service` 先完成绑定，
  并 `Before=NetworkManager.service`。
* **NM 运行状态不持久化**（NM 1.50 也没有 `state-file` 键），重启重建；
  重启后 Wi-Fi 由 NM 的 autoconnect 重新关联（隐藏网络除外，见限制）。
* **nmtui 不启用**：newt 0.52.23 的源码包在 pagure.io 归档后 404，
  Debian 的 orig 包哈希也对不上；`nmcli` 足够，图形界面交给 `shui-settings`。
* **DNS 用 resolved stub 而不是直写上游**：应用统一问 `127.0.0.53`，
  上游由 NM 按连接下发；镜像里没有 `getent`，验收用 `ping 域名` 或
  `resolvectl query`。

构建期的两个次序陷阱：

1. Buildroot 在 **post-build 之后**还会跑 `systemctl preset-all`
   （ROOTFS_PRE_CMD），默认 preset 会把 `systemd-networkd` 和
   `network.service` 重新 enable。必须用编号更小的
   `/etc/systemd/system-preset/00-shuios.preset` 覆盖。
2. NM 包会先建一个真实的 `system-connections` 目录，直接 `ln -sfn` 会在
   目录里生成自指链接，NM 写配置时报只读。必须先 `rm -rf` 再建链接。

无真 Wi-Fi 硬件的验证方法见 `docs/05` V22：mac80211_hwsim 造两枚虚拟
无线电，hostapd 做 AP、NM 做客户端；**两端同机，ping 通不代表无线链路
可用**，要看 `nmcli state 100`、`iw link` 和 AP 的 station dump。

## 14. 设置中心（shui-settings）

组件与定位：

| 组件 | 版本 | 作用 |
| --- | --- | --- |
| `shui-settings` | 0.1.0 | GTK3 设置中心（网络 / 声音 / AI / 关于） |
| `nmcli` | NetworkManager 1.50.2 | 后端：设备状态、Wi-Fi 扫描、连接激活/断开 |
| NM keyfile | — | 连接配置 `0600`，经符号链接落数据分区 |
| `wpctl` | WirePlumber 0.5.5 | 声音页后端：默认 sink 的音量/静音、设备名、测试音前的服务状态 |
| `shui-ctl ai` / `shuiosd` | 本仓库 | AI 页后端：读写 `/var/lib/shuios/state/ai.json`、测试连接；密钥只经 stdin/0600 文件传递 |

关键布局与入口：

```
/usr/bin/shui-settings
/usr/share/applications/shui-settings.desktop   # shui-panel 启动台扫描
/etc/shuios/sway-config                          # Win+I + 两条 for_window
```

```conf
for_window [app_id="shui-settings"] floating enable, resize set 900 620, move position 174 32
for_window [app_id="shui-settings" title="^连接到 Wi-Fi$"] resize set 420 220, move position 430 290
bindsym $mod+i exec /usr/bin/shui-settings
```

设计决定：

* **不引新依赖**：GTK3 与 nmcli 镜像里已有；不重做网络后端。
* **nmcli 只用 argv**：SSID/密码不进 shell，避免拼接注入；terse 输出由
  `split_terse()` 处理 `\:` 转义。
* **密码写盘**：GKeyFile 先写 `mkstemp`（0600）临时文件再 rename，避免中间态
  可读；已有配置按 `[wifi] ssid` 查找后补 psk，找不到才新建
  `shui-settings-<hash>.nmconnection`。
* **线程模型**：扫描、状态刷新、连接各用 `g_thread_new`，结果经 `g_idle_add`
  回 GTK 主线程；窗口关闭必须 `destroy → gtk_main_quit`，否则进程残留。
* **能力边界**：802.1X/WEP 在行点击时明确拒绝；隐藏网络保持 NM 语义（需
  定向配置，不建 GUI 入口）。
* **声音页也只用 argv**：音量/静音用 `wpctl set-volume @DEFAULT_AUDIO_SINK@
  N%` / `set-mute`，测试音用 `/bin/sh -c 'speaker-test ... & p=$!; sleep 9;
  kill $p'`（`speaker-test` 在 PipeWire 下播完不退出，必须有看门狗）。
* **音量持久化**：WirePlumber 不保存默认 sink 音量，改音量/静音后由设置页和
  任务栏写 `/var/lib/shuios/state/audio.conf`（`VOLUME` / `MUTE`），会话启动
  回放；细节见 §17。
* **初始页必须 show_all 后切**：`gtk_stack` 用 CROSSFADE 时，在
  `gtk_widget_show_all()` 之前切页不生效；导航用 `row-activated`（单击或回车；
  用 `row-selected` 会让 Tab 焦点锁在侧栏），并在进入声音页时刷新数值。
* **AI 页不碰明文密钥回读**：保存时把输入框内容写进 0600 临时文件，调用
  `shui-ctl ai set --key-file` 后立即 unlink；页面只显示 `key_hint()` 末四位。
  `ai.test` 在 GThread 里执行，结果必须 `g_idle_add()` 回主线程。

开发/验证注意：

* 根分区只读（squashfs）：改 `/etc/shuios/sway-config` 或往
  `/usr/share/applications` 加 `.desktop` 需要 bind mount / tmpfs 叠加，
  正式文件必须走镜像构建。
* 测试 AP（hwsim + hostapd）没有 DHCP：GUI 新建配置是 `ipv4.method auto`，
  测试时预置 manual 配置验证密码链路；自动取址待真实网络验证。

gtk_layer_set_namespace(GTK_WINDOW(g_window), "shui-panel");
gtk_layer_set_layer(GTK_WINDOW(g_window), GTK_LAYER_SHELL_LAYER_TOP);

`exclusive_zone` 是关键：平铺/最大化的窗口会自动停在任务栏上沿（实测

`shui-panel-menu`）：layer surface 不能挂 xdg_popup，GtkMenu 弹不出来。
sway 规则：

```conf
for_window [app_id="shui-panel-menu"] floating enable, border none, sticky enable, resize set 460 520, move absolute position 410 232
bindsym $mod+d exec /usr/libexec/shuios/shuios-launch
```

坐标必须用 `move absolute position`：`move position` 相对工作区原点，工作区
有过窗口后原点变成 (16,16)（outer gaps），同一规则会漂 16px（V24 实测）。

按钮模型（合并式，Windows 11 风格）：

- 固定项（终端/文件/浏览器/商店）按 `app_id` 匹配运行窗口；未固定的应用运行
  后动态追加按钮（最多 16 个）。
- 点击：未运行→启动；运行未聚焦→聚焦；运行且聚焦→`move scratchpad` 最小化；
  再点从 scratchpad 拉回。
- 右键：直接 `kill` 该应用（layer 面不能弹上下文菜单；后续要做只能再起独立
  toplevel）。
- 运行指示：图标下方 3px `ACCENT` 短线，运行 14px、聚焦 22px。

```
sway IPC ──shui-ctl windows --follow──▶ shui-panel 按钮/短线

layer-shell 协议 ──exclusive_zone 40──▶ 平铺窗口自动避让
```

开发/验证注意：

- 用 `swaymsg -t get_tree` 验证 layer 面时，找 `"namespace": "shui-panel"`

- 自动点击要先 `seat seat0 cursor set`，**等 250ms** 再 press：cursor set 是异步

## 16. 锁屏与空闲锁定（`shui-lock` / `shui-idle`）

组件：

| 组件 | 作用 |
| --- | --- |
| `shui-lock` | 全屏锁屏：暗化壁纸、时钟/日期、用户卡片、密码框、解锁、重启/关机（二次确认） |
| `shui-idle` | 空闲计时 + 锁定看门狗；`/etc/shuios/idle.conf` 的 `timeout=`，CLI `--timeout` 覆盖 |
| `shui-key` | 验收工具：Wayland 虚拟键盘（`zwp_virtual_keyboard_manager_v1`），`--text/--combo/--key` |

锁屏 layer 绑定（`shui-lock.c`）：

```c
gtk_layer_init_for_window(GTK_WINDOW(g_window));
gtk_layer_set_namespace(GTK_WINDOW(g_window), "shui-lock");
gtk_layer_set_layer(GTK_WINDOW(g_window), GTK_LAYER_SHELL_LAYER_OVERLAY);
gtk_layer_set_anchor(GTK_WINDOW(g_window), GTK_LAYER_SHELL_EDGE_TOP, TRUE);
gtk_layer_set_anchor(GTK_WINDOW(g_window), GTK_LAYER_SHELL_EDGE_BOTTOM, TRUE);
gtk_layer_set_anchor(GTK_WINDOW(g_window), GTK_LAYER_SHELL_EDGE_LEFT, TRUE);
gtk_layer_set_anchor(GTK_WINDOW(g_window), GTK_LAYER_SHELL_EDGE_RIGHT, TRUE);
gtk_layer_set_exclusive_zone(GTK_WINDOW(g_window), -1);   /* 整块输出 */
gtk_layer_set_keyboard_mode(GTK_WINDOW(g_window),
                            GTK_LAYER_SHELL_KEYBOARD_MODE_EXCLUSIVE);
```

`exclusive_zone=-1` 是 layer-shell 的「使用整块输出」语义（wlroots
`wlr_scene_layer_surface_v1_configure()`：`exclusive_zone == -1` 时 bounds 取
full_area）。写 0 会被任务栏的独占区裁掉 40px，锁屏底部露出任务栏（V25 踩过）。

防绕过是两层：

```conf
mode "shui-lock" {
    bindsym Mod4+Shift+F12 nop
}
```

- layer 键盘模式 EXCLUSIVE：按键不进入任何客户端，只给锁屏。
- sway binding mode：锁屏启动后 `swaymsg mode shui-lock`，默认 `Win+*`
  绑定在当前模式下不生效；解锁或异常退出由锁屏/看门狗恢复 `mode default`。

鉴权链路：

```c
/* 桌面是 systemd system service（root），/etc/shadow 可读；镜像无 PAM */
struct crypt_data cd = {0};
crypt_r(password, shadow_hash, &cd);
/* strcmp 后清零 cd */
```

锁屏单实例：`flock(/run/shuios/lock.lock)` + `/run/shuios/lock.pid`。
shui-idle 每 500 ms 检查 pidfile 里的 PID；进程消失则删 pidfile、通过
`swaymsg mode default` 恢复快捷键，并重新计时（避免死锁循环）。

空闲检测直读 `/dev/input/event*`（EV_KEY/EV_REL/EV_ABS/EV_SW），不是 Wayland
idle-notify；合成注入（shui-key）不经过 evdev，因此不会重置空闲计时。

`shui-key` 的修饰键修正（wlroots 0.20）：

```c
zwp_virtual_keyboard_v1_key(g_vk, 0, keycode, state);   /* update_state=false */
xkb_state_update_key(g_state, keycode + 8, state ? XKB_KEY_DOWN : XKB_KEY_UP);
zwp_virtual_keyboard_v1_modifiers(g_vk, depressed, latched, locked, group);
```

合成器不会从按键事件推导 Super/Shift；不发 `modifiers`，`Win+L` 只会发出
单独的 `l`，绑定不触发（V25 踩过）。

登录/电源边界：镜像没有 PAM/greetd，锁屏解锁后直接回到同一个 root 会话；
「注销」是 `swaymsg exit`，由 `shuios-desktop.service`（Restart=always）
重建会话；关机/重启直接 `systemctl poweroff|reboot`。

## 17. 音频栈（PipeWire + WirePlumber）

组件与拓扑：

| 组件 | 版本 | 作用 |
| --- | --- | --- |
| `pipewire` | 1.2.8 | 音频图/混音器，占 ALSA 设备（VMware HDA → `alsa_output.pci-0000_00_12.0.analog-stereo`） |
| `wireplumber` | 0.5.5 | 策略/设备管理，创建默认 sink，`wpctl` 的后端 |
| `pipewire-pulse` | 1.2.8 | PulseAudio 协议兼容层；`pactl`、GStreamer `pulsesink`、WebKit 都接它 |
| `pulseaudio`（仅库） | 17.0 | 客户端库；不装 daemon |
| GStreamer pulse 插件 | 1.24.13 | 文件是 `libgstpulseaudio.so`（不是 `libgstpulse.so`） |

会话启动顺序（`shuios-session.sh` 的 `start_audio()`）：

```
XDG_RUNTIME_DIR=/run/shuios/compositor
  pipewire          → 等 pipewire-0 套接字（最多 5 s）
  wireplumber       → 建设备/默认 sink
  pipewire-pulse    → Pulse 兼容套接字
  回放 audio.conf   → 等 @DEFAULT_AUDIO_SINK@（最多 10 s）+1 s 稳定，
                      再 wpctl set-volume / set-mute
```

设计决定：

* **系统级单元全部 mask**：Buildroot 的 `pipewire.service` /
  `pipewire.socket` / `pipewire-manager.socket` / `wireplumber.service` /
  `wireplumber@.service` 以 `pipewire` 用户、`/run/pipewire` 运行，会先占住
  HDA。post-build 删除 wants 链接并 `ln -sf /dev/null`，由会话（root，
  `/run/shuios/compositor`）启动唯一实例；否则默认输出会变成 Dummy。
* **ALSA 兼容不是并列两套**：`/etc/asound.conf` 的 `pcm.!default` 与
  `ctl.!default` 都是 `type pipewire`，`aplay`/`speaker-test` 自动进
  PipeWire；混音由 PipeWire 完成，不再需要 dmix。
* **音量持久化外挂**：WirePlumber 不落盘默认 sink 音量（冷启动回 40%），
  `/var/lib/shuios/state/audio.conf` 存 `VOLUME=` / `MUTE=`，由
  `shui-settings` 声音页与 `shui-panel` 音量按钮写入；会话启动回放。
  这是本项目补的薄状态层，不是 WirePlumber 原生行为。
* **UI 全部 argv 调 `wpctl`**：没有链接 libpipewire；音量/静音/设备名都走
  `wpctl get-volume` / `set-volume` / `set-mute`，失败时 UI 置灰并显示
  “音频服务不可用”。
