# 架构总览

本文说明 shuios 为什么这么分层、每一层承担什么、以及"不可变根"和
"智能体一等公民"这两个目标在代码里的落点。

## 1. 设计起点：三种身份

任何操作系统设计先要回答"谁在用这台机器"。shuios 假设三种身份并存：

| 身份 | 关心什么 | shuios 的回应 |
| --- | --- | --- |
| **人** | 想用自然语言指挥机器 | `shui`：AI 原生 shell |
| **智能体** | 需要明确的边界与可观测性 | `shuiosd`：cgroup 隔离 + 日志 + 工具总线 |
| **自动化脚本** | 需要稳定的非交互接口 | `shui-ctl`：一次性命令，输出可 `grep` |

三者共用同一套底层：JSON Lines RPC、同一个 cgroup 树、同一份日志。

## 2. 分层

### 2.1 内核层

内核不是发行版，但**内核配置就是产品设计**。shuios 的内核片段
（`br2-ext/board/shuios/common/kernel-shuios.fragment`）刻意做三件事：

1. **把 cgroup v2 的控制器全部内置**——`memory`/`pids`/`cpu`/`io` 不开
   subtree_control 就等于没有资源隔离；
2. **把只读根所需的东西内置**——squashfs（xz/zstd）、overlayfs、tmpfs；
3. **把沙箱原语内置**——landlock、seccomp filter、user namespace、BPF，
   为 v0.2 的更严格隔离铺路。

同时把 GPU 驱动、常见网卡设成**模块**：内核镜像小，启动快，硬件支持靠
`/lib/modules` 按需加载。

### 2.2 init 层：systemd

选 systemd 不是为了"现代"，而是因为它做了三件我们不打算重写的事：

* cgroup v2 树的建立与委托（`shuiosd` 才能在 `/sys/fs/cgroup/shuios/` 下建子树）；
* 服务依赖与启动顺序（`shuios-storage` 必须在 `shuiosd` 之前）；
* 日志汇聚（`shuiosd` 只往 stderr 写，剩下的交给 journal）。

`shuiosd.service` 里有 `KillMode=control-group`：即便 `shuiosd` 崩溃，
它派生的智能体也会被 systemd 一并回收，不会留下孤儿进程。

### 2.3 运行时层：shuiosd

这是 shuios 的核心，也是唯一"发明"出来的层。它的职责边界很窄：

```
控制平面（/run/shuios/shuiosd.sock）
    │   JSON Lines，一行一请求
    ▼
监督器 ──┬─ cgroup v2 目录  /sys/fs/cgroup/shuios/<name>/
         ├─ 进程（setsid，独立进程组）
         ├─ 日志文件        /var/log/shuios/agents/<name>.log
         └─ stdin 管道      （agent.send 写入）
    │
    ▼
内置 MCP 工具（模型可调用的系统能力）
```

**为什么每个智能体要 setsid**：把它放进独立进程组，击杀时一条
`cgroup.kill` 就能整组带走；同时也让智能体内部的作业控制不与宿主冲突。

**为什么日志既写文件又留内存尾部**：文件用于事后审计，内存环形缓冲
（400 行）让 `agent.logs` 能立刻返回，不必读盘。

**为什么不用容器**：智能体需要的是"资源边界 + 可观测"，而 cgroup v2 恰好
就是这两件事的内核原语。拉 containerd 会让最小镜像多出 100MB+ 且引入
一整套我们不需要的抽象。

### 2.4 界面层：shui 与 shui-ctl

`shui` 把输入分成三类，这个分流是整个用户体验的核心：

```
/xxx     → 内置命令（确定性的，不经过模型）
!xxx $xxx → 交给 /bin/sh（逃逸舱口，永远可用）
其余      → 自然语言 → 推理服务（本地/远程，经 shuiosd）→ mcp.call 工具循环
```

第三类是重点：模型**不直接执行 shell**，它只能调用 `shuiosd` 暴露的工具。
这样"模型能做什么"由系统决定，而不是由提示词决定——这是安全边界，不是
风格偏好。

## 3. 不可变根

### 3.1 布局
```
/dev/sda1  ESP        FAT32     GRUB + 内核 + grubenv（A/B 状态）
/dev/sda2  root-a     squashfs  根槽 A（只读）
/dev/sda3  root-b     squashfs  根槽 B（升级目标，初始为空）
/dev/sda4  data       ext4      持久化
```

四个分区都带**固定 PARTUUID**，GRUB 与内核都用 `PARTUUID=` 定位，
因此 SATA / USB / NVMe 设备名不同也不影响启动：

| 分区 | PARTUUID |
| --- | --- |
| ESP | `5b1e0a00-0000-4000-8000-0000000000e1` |
| root-a | `5b1e0a00-0000-4000-8000-0000000000a1` |
| root-b | `5b1e0a00-0000-4000-8000-0000000000b1` |
| data | `5b1e0a00-0000-4000-8000-0000000000d1` |

这些常量在 `crates/shuios-update/src/slots.rs` 与 `genimage.cfg` 里各出现一次，
必须保持一致（有单元测试检查唯一性与长度）。

`/etc/fstab` 里根是 `ro,noatime`，其余可写路径全是 tmpfs 或数据分区的绑定：

```
/data/workspace  →  /workspace          （用户唯一持久目录）
/data/shuios/models → /var/lib/shuios/models
/tmp /var/tmp /var/log /root → tmpfs    （重启即消失）
```

### 3.2 为什么这样做

1. **智能体改不坏系统**：无论它误删 `/usr` 还是写坏 `/etc`，重启即恢复。
2. **升级变成"换一个 squashfs"**：v0.2 的 A/B 双分区就是这么来的。
3. **取证简单**：系统状态与用户数据在物理上分离。

### 3.3 代价（必须承认）

* 改系统配置要重新构建镜像，不能"就地改"；
* 日志默认不持久（需要的话加挂 `/data` 下的目录）；
* 需要 root 才能 `mount --bind`，所以 `shuios-storage` 是 systemd oneshot。

## 4. 一次自然语言请求的完整路径

```
用户: "看看 /workspace 有什么"
  │
  ├─ shui 读取 ai.status（shuiosd 的运行时配置，密钥不出守护进程）
  ├─ 组装 system prompt：内置工具清单 + JSON 工具调用协议
  ├─ shui → shuiosd 的 ai.chat（Unix 套接字，回环）
  ├─ shuiosd → POST /chat/completions
  │     本地：http://127.0.0.1:8080（llama-server，同机回环）
  │     远程：https://api.deepseek.com/v1 等（curl + 系统 CA，
  │           密钥只写进 0600 请求头文件）
  │
  ├─ 模型回复 {"tool":"fs.list","arguments":{"path":"/workspace"}}
  ├─ shui 识别出工具调用 → shuiosd 的 mcp.call 方法
  ├─ shuiosd 执行（白名单检查 / 权限 / 审计）
  ├─ 结果回填给模型
  │
  └─ 模型给出中文结论 → shui 打印
```

默认的本地路径不需要互联网：推理在本机、工具在本机、协议在回环套接字上。
选择远程提供商时，唯一的外网连接是 `shuiosd` 到服务商的一跳；`shui`、
设置中心和命令行都看不到密钥。

## 5. 桌面层（v0.1 起就有）

shuios 早期设计是无图形界面的纯终端系统，后来明确改为**完整桌面版**。
选型受 Buildroot 生态约束（它没有 Xorg、没有 chromium/firefox、没有 GTK4）：

| 层 | 组件 | 为什么是它 |
| --- | --- | --- |
| 显示协议 | **Wayland** | 现代、无 X11 的历史包袱 |
| 合成器/桌面 | **swayfx 0.6**（wlroots 0.20） | 平铺 + 动画，layer-shell 任务栏；VMware vmwgfx 走 GLES2 轻效档 |
| 图形驱动 | **mesa3d + LLVM** | llvmpipe 软件渲染（虚拟机可用）+ i915/iris（Intel 核显）+ vmwgfx |
| 终端 | **foot** | Wayland 原生、极轻 |
| 浏览器 | **shui-browser**（WebKitGTK 2.48） | 自研外壳：标签/下载/中文错误页（V18） |
| 文件管理器 | **shui-files**（GTK3） | 浏览/新建/重命名/删除/隐藏文件/打开，Win+E（V21） |
| AI 推理 | **shui-llm + shuiosd `ai.*`** | 本地 llama.cpp / 远程 OpenAI 兼容提供商；密钥只存 `/var/lib/shuios/state/ai.json`（0600），设置中心 AI 页与 `shui-ctl ai` 管理（V27） |
| 音频 | **PipeWire 1.2.8 + WirePlumber 0.5.5 + pipewire-pulse** | ALSA 经 `asound.conf` 接入，多程序混音；任务栏/设置音量、静音、重启保留（V26）；系统级 pipewire 单元在镜像里被 mask |
| 任务栏 / 开始菜单 | **shui-panel**（gtk-layer-shell） | 底部 40px 通栏 + 合并式窗口按钮 + 开始菜单（锁屏/注销/重启/关机）；无顶栏、无 Dock（V24/V25） |
| 锁屏 | **shui-lock**（GTK3 + gtk-layer-shell） | layer OVERLAY 全屏 + 键盘独占 + sway `shui-lock` binding mode；`/etc/shadow` + `crypt_r()` 校验（V25） |
| 空闲锁定 | **shui-idle** | 直读 evdev 计时，默认 600 s 锁定；锁进程异常消失时看门狗恢复 `mode default`（V25） |
| 工具包 | GTK3（Wayland 后端） | 自研界面统一用它 |

**会话布局**：

```
tty1  → swayfx（DRM/GL）→ 自动拉起：swaybg 壁纸 + shui-panel（底部任务栏）
        + shui-idle（空闲锁定：默认 600 s）
        + pipewire → wireplumber → pipewire-pulse（音频；音量/静音从
          /var/lib/shuios/state/audio.conf 回放）
        开机不预开应用；终端/文件/浏览器/商店/设置从任务栏或开始菜单启动
        Win+E 打开 shui-files；Win+I 打开 shui-settings；Win+L 锁定
tty2+ → agetty 自动登录 root → 直接进 shui（文本模式，SSH 同体验）
```

两边都是同一个 `shui`，所以"有桌面"没有牺牲"能用 SSH 指挥机器"。

**没有显示设备时**（无 DRM 的容器/虚拟机）`shuios-session` 会自动退到
Weston 的 headless 后端，而不是无限重启。

## 6. 明确的非目标

* **不做 Windows/macOS 替代品**：桌面存在是为了让 AI 系统"可见、可操作"，
  不是为了跑 Office。
* **不做集群编排**：单机智能体运行时；多机留给外部系统。
* **不做"AI 防火墙"式的策略引擎**：v0.1 的权限模型是文件白名单 + cgroup，
  刻意保持可解释。
* **不预装 Chrome 级浏览器**：Buildroot 没有 chromium/firefox；需要时
  用外部发行版基座，见 docs/04-路线图.md 的未决问题。
